このページは通知の**管理者側**を扱います。イベントがどのようにメッセージになるか、そしてその背後にあるシステム管理の 3 つのオブジェクトです。受信者から見た受信トレイ（通知を読む、ミュートする）については、*使い方*の[通知](/docs/use/notifications)を参照してください。

## 通知のパイプライン [#the-notification-pipeline]

通知は単一のレコードではありません。4 つの段階を流れます。

```text
emit() + explicit audience  →  Notification Event  →  recipients, filtered by Preference  →  Inbox Message
```

1. **`emit()`**：アプリケーションのコードがイベント（承認の申請、レコードの共有、招待の送信）を発生させ、**その対象者を指定します**。対象者は必須の入力で、誰に通知するかを決めるのはこれです。
2. **Notification Event**（`sys_notification`）：各 `emit()` は受け入れの行を 1 つ書き込みます。これは配信の判断が行われる前の、*何が起きたか*の診断ログです。読み方は[監査ログ](/docs/operate/audit-logs)を参照してください。
3. **ルーティング**：各イベントについて、ObjectOS はプロデューサーが渡した対象者を受信者に展開し、各受信者がそのチャネルでそのトピックを許可しているか（**Preferences**）を確認し、受け付けられた各配信をそのチャネルに渡します。チャネルがそれをレンダリングします。チャネルが何*から*レンダリングするかはチャネルによって異なります。メールと SMS は **Notification Templates** をレンダリングし、アプリ内の受信トレイはそうしません（[各チャネルが何をレンダリングするか](#what-each-channel-renders)を参照）。
4. **Inbox Message**（`sys_inbox_message`）：受信者が実際に受信トレイで目にする、具体化されたユーザーごとの結果です。

Preferences、Subscriptions、Templates は管理者 / システム側の設定です。Inbox Messages はユーザー側の出力です。

### ルーティングがどう解決されるか [#how-routing-resolves]

1 つのイベントについて、誰が何を受け取るかを決める入力は次のとおりです。

| 入力 | 答える問い |
|---|---|
| `emit()` に渡される対象者 | *誰が受け取るか？* プロデューサーが受信者を指定します。リストに誰かを載せる入力はこれだけです |
| Notification Preference | *この受信者はここでそれを許可しているか？* トピックとチャネルに対するユーザーごとのミュート / 許可で、すべての（受信者 × チャネル）の組に適用されます |
| Notification Template | *どう書かれるか？* **メール**と **SMS** のチャネルでレンダリングされる件名と本文です。アプリ内の受信トレイはこれらの行を読みません。[各チャネルが何をレンダリングするか](#what-each-channel-renders)を参照してください |
| Notification Subscription | *誰が継続的な関心を宣言したか？* 管理者が作成する行で、**イベントのルーティング時には参照されません** |

プロデューサーの対象者がその受信者に解決され、その受信者の設定がそのチャネルでそのトピックをミュートしていなければ、受信者の受信トレイに届きます。デフォルトは許可なので、設定の行を持たない受信者も通知を受け取ります。また、必須のトピック（セキュリティアラートなど）は設定を完全にすり抜けます。

> **警告：** Subscription の行は何もルーティングしません。サブスクリプションから受信者への展開は**配線されていません**。`emit()` は明示的な対象者を必要とし、上のパイプラインのどこにも、トピックのサブスクリプションを受信者に展開するものはありません。すべての配信はプロデューサーが渡した対象者から来ます。そのため、Setup の **Notification Subscriptions** のグリッドは管理者が作成するデータであり、稼働中のルーティングのコントロールではありません。行を一時停止しても（`enabled = false`）何も止まらず、行を追加しても何も配信されません。

これは、このページで説明する通知のパイプラインについての記述です。ObjectOS の上で動く機能や連携が、独自の目的でこれらの行を使って何をするかについての主張ではありません。ADR-0012 と ADR-0030 は、サブスクリプション駆動のルーティングを、現在の動作ではなく**目標とする状態**として記述しています。これらの行をルーティングに関係させるはずの展開は構築されておらず、予定もされていません。もし構築されれば、ここに記述した動作もそれとともに変わります。

Preferences と Templates はプラットフォームが初期投入して保守するので、それらのリストビューに表示されるのはほとんどがシステムの生成した行です。Subscription の行は管理者が Setup から作成するもので、そのためにそのグリッドがルーティングのコントロールのように見えてしまいます。

## Notification Preferences [#notification-preferences]

**Setup → Configuration → Notification Preferences**（`sys_notification_preference`）にあります。

ユーザー × トピック × チャネルごとのトグル（ミュート / 許可）で、管理者によるグローバルなデフォルトを持ちます。設定は、ある受信者があるトピックをあるチャネルで受け取るかどうかを決めます。

| フィールド | 目的 |
|---|---|
| `user_id` | 設定が属するプリンシパル |
| `topic` | 通知のトピック（例：`project.digest`） |
| `channel` | 配信チャネル（アプリ内、メール……） |
| `enabled` | ブール値。そのユーザーについて、このトピック / チャネルを許可するかミュートするか |
| `digest` | そのトピックをまとめて送る周期 |
| `quiet_hours` | 配信を抑制する時間帯を表す JSON |
| `created_at` / `updated_at` | 監査用のタイムスタンプ |

> エントリは、そのソースとなるアクション（たとえば *Submit for Approval*、*Share*、*Invite*）が最初に実行されたときに自動的に現れます。設定の行を手で作成することはまれです。リストは、管理者のデフォルトを調整したり、うるさいトピックをミュートしたりするのに使ってください。

## Notification Subscriptions [#notification-subscriptions]

**Setup → Configuration → Notification Subscriptions**（`sys_notification_subscription`）にあります。

プリンシパルによる通知のトピックへの**継続的なサブスクリプション**です。この行は、誰かがそのトピックに関心を宣言したことを記録します。これは参照用のデータです。配信の経路のどこもこれを読まないので、サブスクリプションの行は受信者を追加することも削除することもしません（[ルーティングがどう解決されるか](#how-routing-resolves)を参照）。

| フィールド | 目的 |
|---|---|
| `topic` | サブスクライブするトピック |
| `principal` | サブスクライバー。セレクターの文字列です。[`principal` に何を入力するか](#what-to-type-in-principal)を参照してください |
| `enabled` | ブール値。行を有効または一時停止としてマークします。どの配信もこれを参照しません |

### `principal` に何を入力するか [#what-to-type-in-principal]

`principal` はピッカーではなく、1 つのテキストフィールドです。値は**セレクターの文字列**で、そのプレフィックスによって、値が何と照合されるかが決まります。以下の形式は、プラットフォームの受信者リゾルバーがどのセレクターの文字列についても**受け付ける**ものです。`emit()` の対象者を書くのと同じ文法です。認識されるプレフィックスのない値は素のユーザー ID として読まれます。そのため `sales_manager`（または `Sales team`）と入力すると、意図したグループではなく、存在しないユーザーを指定することになります。

| 値 | 解決先 | 例 |
|---|---|---|
| `role:name` | 組織内で、組織メンバーシップの階層がその名前であるすべての人（`sys_member.role`） | `role:admin` |
| `team:id` | そのチームのすべてのメンバー。ラベルではなくチームの **ID** で照合します（`sys_team_member.team_id`） | `team:team_123` |
| `user:id` | ユーザー ID で指定した、その 1 人のユーザー | `user:usr_123` |
| `owner_of:object:id` | その 1 件のレコードの所有者。レコードが持つ最初の所有者 / 担当者のフィールドです | `owner_of:invoice:inv_123` |
| メールアドレス | メールアドレスが一致するユーザー。**どのユーザーにも一致しないアドレスは、拒否されずにそのまま**受信者 ID として保持されます | `ada@example.com` |
| `id` | 認識されるプレフィックスなし。値全体が素のユーザー ID として扱われます | `usr_123` |

このリストはリゾルバーが受け付けるものであって、サブスクリプションの行のために設計された契約ではありません。`owner_of:` とメールの形式があるのは、すべてのセレクターの文字列が同じリゾルバーを通るからです。どちらかが継続的なサブスクリプションにふさわしいかどうかは、プラットフォームがまだ決めていない未解決の問題です。

> **ここでの `role:` は組織メンバーシップの階層を意味し、職務ではありません。** 階層は [`owner`、`admin`、`delegated_admin`、`member`](/docs/configure/users#organization-membership-tiers) で、ユーザーが組織の中で持つ立場です。職務は[ポジション](/docs/configure/permissions/positions)で、ポジションの名前はここでは指定できません。`role:sales_manager` は誰にも一致しません。*Role* は ObjectOS のほかのあらゆる場所で廃止された用語です（機能は権限セット、配布はポジション）。組織メンバーシップの階層が唯一の例外で、このセレクターもそれを同じように綴ります。

セレクターの背後にあるディレクトリの検索は、意図的にベストエフォートです。検索が外れたことでイベントが失敗することはありません。したがって、何にも一致しないセレクターは**黙ってゼロ人の受信者**に解決されます。行は有効なまま有効化されたままで、それについて何も報告されません。一致しないメールアドレスはさらに厄介です。それ自体が受信者 ID として保持されるので、入力ミスは決して届かない受信者になります。トピックが誰にも届かないときは、まずプレフィックスと値の綴りを確認してください。

## Notification Templates [#notification-templates]

**Setup → Configuration → Notification Templates**（`sys_notification_template`）にあります。

**（トピック × チャネル × ロケール）** ごとのレンダリングのテンプレートで、**メール**と **SMS** のチャネルが読みます。テンプレートは、イベントのペイロードを、それらのチャネルが送る件名と本文に変換します。アプリ内の受信トレイはこれらの行を読みません。[各チャネルが何をレンダリングするか](#what-each-channel-renders)を参照してください。

| フィールド | 目的 |
|---|---|
| `topic` | このテンプレートがレンダリングするトピック |
| `channel` | レンダリングされた出力の送信先チャネル |
| `locale` | このレンダリングのロケール。受信者のものではなく、通知自身のものです |
| `version` | テンプレートのバージョン番号 |
| `subject` | レンダリングされるタイトル |
| `body` | メッセージの本文（Markdown） |
| `format` | 本文の出力形式 |
| `is_active` | ブール値。このテンプレートをレンダリングに使うかどうか |

ロケールは受信者ではなく**通知**で照合されます。配信は、プロデューサーが `payload.locale` を設定していればそれで、そうでなければデプロイメントのデフォルトでレンダリングされます。受け取る人からロケールを解決するものは何もないので、1 回の emit は、届くすべての受信者に対して単一のロケールでレンダリングされます。あるトピックに `es` と `en` の行を作成すると、プロデューサーが選べる 2 つのレンダリングができるのであって、2 人の受信者がそれぞれ自分の言語で読めるようになるわけではありません。

これらのオブジェクトは**システム管理**です。行はプラットフォームと実行している機能によって初期投入されるので、作業のほとんどは、レコードを一から作成することではなく、テンプレートの内容を編集したり、`is_active`、`enabled`、設定のデフォルトを切り替えたりすることです。

### 各チャネルが何をレンダリングするか [#what-each-channel-renders]

レンダリングはチャネルごとに行われ、上の行を読むのは 2 つのチャネルだけです。

| チャネル | レンダリングの元 |
|---|---|
| **メール** | （トピック、`email`、ロケール）に一致する Notification Template。一致する有効な行がなければ、通知自身のタイトルと本文がそのまま送られます |
| **SMS** | （トピック、`sms`、ロケール）に一致する Notification Template。同じフォールバックがあります |
| **アプリ内の受信トレイ** | **Notification Template ではありません。** 受信トレイの行は、通知自身のタイトルと本文から書かれます。プロデューサーがタイトルを設定しなかった場合はトピックです。通知が代わりにメールテンプレートを指定している場合、受信トレイはそれをレンダリングします。メールサービスを通じて（名前、ロケール）で解決される `sys_email_template` の行で、[メール](/docs/configure/email#templates)に記載されています。それをレンダリングできるメールサービスがなければ、その配信はフォールバックせずに失敗します |

> **警告：** `inbox` は**デフォルト**のチャネルです。チャネルを指定しない通知はそこに配信され、ほかのどこにも配信されません。そのため、管理者が最も目にしやすい配信は、Notification Template を決して読まない配信です。ここでテンプレートの行を編集すると、メールと SMS が送る内容は変わりますが、アプリ内のメッセージは何も変わりません。このページは現状の配線を記述しており、受信トレイがこれらの行とつながる将来を予告するものではありません。
