本页讲的是通知的**管理员一侧**：事件如何变成消息，以及支撑它们的三个由系统
管理的对象。收件人视角的收件箱 —— 阅读和静音通知 —— 参见*使用*一节中的
[通知](/docs/use/notifications)。

## 通知管道 [#the-notification-pipeline]

一条通知不是单独一条记录。它流经四个阶段：

```text
emit() + explicit audience  →  Notification Event  →  recipients, filtered by Preference  →  Inbox Message
```

1. **`emit()`** —— 应用代码发起一个事件（审批已提交、记录已共享、邀请已
   发送），并**指定它的受众**。受众是必需的输入，由它决定通知谁。
2. **通知事件**（`sys_notification`）—— 每次 `emit()` 写入一行入口记录。这是
   在做出任何投递决定之前，*发生了什么*的诊断日志。如何阅读它，参见
   [审计日志](/docs/operate/audit-logs)。
3. **路由** —— 对每个事件，ObjectOS 把生产方传入的受众展开为收件人，检查每个
   收件人是否允许该主题在该渠道上投递（**偏好**），并把每个被接受的投递交给
   相应的渠道，由渠道负责渲染。渠道*基于什么*渲染因渠道而异：邮件和短信渲染
   **通知模板**；应用内收件箱则不用（参见
   [各渠道渲染什么](#what-each-channel-renders)）。
4. **收件箱消息**（`sys_inbox_message`）—— 收件人在收件箱中实际看到的、按用户
   生成的结果。

偏好、订阅和模板是管理员 / 系统一侧的配置。收件箱消息是用户一侧的输出。

### 路由如何解析 [#how-routing-resolves]

对于单个事件，决定谁收到什么的输入是：

| 输入 | 它回答的问题 |
|---|---|
| 传给 `emit()` 的受众 | *谁收到它？* —— 由生产方指定收件人，这是唯一能把人放进名单的输入 |
| 通知偏好 | *这个收件人允许在这里收到它吗？* —— 每个用户对该主题和渠道的静音 / 允许设置，作用于每一个（收件人 × 渠道）组合 |
| 通知模板 | *它怎么写？* —— 在**邮件**和**短信**渠道上渲染的主题和正文。应用内收件箱不读取这些行；参见[各渠道渲染什么](#what-each-channel-renders) |
| 通知订阅 | *谁声明过长期的关注？* —— 由管理员编写的行，**在路由事件时不会被参考** |

当生产方的受众解析到某个收件人，且其偏好没有在该渠道上静音该主题时，这个
收件人就会收到收件箱消息。默认是允许，所以没有偏好行的收件人依然会收到通知，
而强制性主题（安全告警之类）会完全绕过偏好。

> **警告：** 订阅行不会路由任何东西。从订阅到收件人的展开**没有接通**：
> `emit()` 需要一个显式的受众，上述管道中没有任何环节会把某个主题的订阅展开
> 为收件人。每一次投递都来自生产方传入的受众，这使得 Setup 中的
> **Notification Subscriptions** 表格只是管理员编写的数据，而不是一个生效的
> 路由控件 —— 暂停一行（`enabled = false`）什么也不会阻止，新增一行也什么都
> 不会投递。

这是对本页所述通知管道的陈述。它并不是在断言运行在 ObjectOS 之上的某项能力
或集成会出于自身目的如何使用这些行。ADR-0012 和 ADR-0030 把订阅驱动的路由
描述为**目标状态**，而不是今天的行为：能让这些行与路由相关的那个展开并没有
被构建，也没有排期。如果将来构建了它，这里描述的行为也会随之改变。

偏好和模板由平台预置并维护，所以这些列表视图中大多是系统生成的行。订阅行是
管理员在 Setup 中编写的那一类，这也是为什么那张表格读起来像一个路由控件。

## 通知偏好 [#notification-preferences]

位于 **Setup → Configuration → Notification Preferences**
（`sys_notification_preference`）。

按用户 × 主题 × 渠道的开关（静音 / 允许），并带有管理员设置的全局默认值。
偏好决定某个收件人是否在某个渠道上收到某个主题。

| 字段 | 用途 |
|---|---|
| `user_id` | 偏好所属的主体 |
| `topic` | 通知主题（例如 `project.digest`） |
| `channel` | 投递渠道（应用内、邮件 ……） |
| `enabled` | 布尔值 —— 为该用户允许或静音此主题 / 渠道 |
| `digest` | 该主题的批量汇总节奏 |
| `quiet_hours` | 抑制投递的时间窗口（JSON） |
| `created_at` / `updated_at` | 审计时间戳 |

> 条目会在其来源动作第一次运行时自动出现（例如 *Submit for Approval*、
> *Share* 或 *Invite*）—— 你很少需要手工创建偏好行。用这个列表调整管理员
> 默认值，或者静音一个吵闹的主题。

## 通知订阅 [#notification-subscriptions]

位于 **Setup → Configuration → Notification Subscriptions**
（`sys_notification_subscription`）。

某个主体对某个通知主题的**长期订阅**：这一行记录的是有人声明过对该主题感
兴趣。它是参考数据 —— 投递路径的任何部分都不会读取它，所以订阅行既不会增加
收件人，也不会移除收件人（参见[路由如何解析](#how-routing-resolves)）。

| 字段 | 用途 |
|---|---|
| `topic` | 被订阅的主题 |
| `principal` | 订阅者 —— 一个选择器字符串；参见[在 `principal` 中填什么](#what-to-type-in-principal) |
| `enabled` | 布尔值 —— 把这一行标记为启用或暂停。没有任何投递会参考它 |

### 在 `principal` 中填什么 [#what-to-type-in-principal]

`principal` 是一个单独的文本字段，而不是选择器：值是一个**选择器字符串**，
它的前缀决定这个值与什么匹配。下面这些形式，是平台的收件人解析器对任何
选择器字符串都**接受**的形式 —— 与 `emit()` 受众所用的语法相同。没有可识别
前缀的值会被当作裸用户 id —— 所以填入 `sales_manager`（或 `Sales team`）
指向的是一个不存在的用户，而不是你想要的那个群体。

| 值 | 解析为 | 示例 |
|---|---|---|
| `role:name` | 组织中成员层级为该名称的所有人（`sys_member.role`） | `role:admin` |
| `team:id` | 该团队的所有成员，按团队 **id** 而不是标签匹配（`sys_team_member.team_id`） | `team:team_123` |
| `user:id` | 那一个用户，按用户 id | `user:usr_123` |
| `owner_of:object:id` | 拥有那一条记录的人 —— 记录上第一个负责人 / 被指派人字段 | `owner_of:invoice:inv_123` |
| 一个邮箱地址 | 邮箱与之匹配的用户。**没有匹配到任何用户的地址会被原样保留**为收件人 id，而不是被拒绝 | `ada@example.com` |
| `id` | 没有可识别的前缀 —— 整个值被当作裸用户 id | `usr_123` |

这张列表是解析器接受的内容，而不是为订阅行设计的契约：`owner_of:` 和邮箱
形式之所以存在，是因为每个选择器字符串都经过同一个解析器。它们是否适合出现
在长期订阅中，是平台尚未定论的开放问题。

> **这里的 `role:` 指的是组织成员层级，而不是职能。** 层级包括
> [`owner`、`admin`、`delegated_admin` 和
> `member`](/docs/configure/users#organization-membership-tiers) —— 即用户在
> 组织中的身份。职能是一个[岗位](/docs/configure/permissions/positions)，而
> 岗位名称在这里无法寻址：`role:sales_manager` 匹配不到任何人。在 ObjectOS 的
> 其他地方，*role* 都是已退役的词汇（能力是权限集，分配是岗位）；组织成员
> 层级是唯一的例外，这个选择器也沿用了同样的写法。

选择器背后的目录查询被有意设计为尽力而为 —— 绝不会因为某次查询没有命中就让
一个事件失败。因此，匹配不到任何东西的选择器会**悄无声息地解析为零个
收件人**：这一行依然有效、依然启用，也不会有任何报告。未匹配的邮箱是更锋利
的边缘 —— 它会被原样保留为收件人 id，所以一个拼写错误就成了一个永远无法
触达的收件人。当某个主题没有送达任何人时，先检查值的前缀和拼写。

## 通知模板 [#notification-templates]

位于 **Setup → Configuration → Notification Templates**
（`sys_notification_template`）。

按**（主题 × 渠道 × locale）**划分的渲染模板，由**邮件**和**短信**渠道读取：
模板把事件内容转换成这些渠道发送的主题和正文。应用内收件箱不读取这些行 ——
参见[各渠道渲染什么](#what-each-channel-renders)。

| 字段 | 用途 |
|---|---|
| `topic` | 此模板渲染的主题 |
| `channel` | 渲染输出的目标渠道 |
| `locale` | 此渲染的 locale —— 是通知自身的，而不是收件人的 |
| `version` | 模板版本号 |
| `subject` | 渲染后的标题 |
| `body` | 消息正文（markdown） |
| `format` | 正文的输出格式 |
| `is_active` | 布尔值 —— 此模板是否用于渲染 |

locale 是按**通知**而不是按收件人匹配的：如果生产方设置了 `payload.locale`，
投递就用它渲染，否则用部署的默认值。没有任何环节会根据接收者来解析 locale，
所以一次 emit 对它触达的每个收件人都以同一个 locale 渲染 —— 为某个主题编写
`es` 和 `en` 两行，是给生产方两种可选的渲染，而不是让两个收件人各自用自己的
语言阅读。

这些对象是**系统管理的**：行由平台以及你运行的能力预置，所以你的大部分工作
是编辑模板内容，或切换 `is_active`、`enabled` 和偏好默认值，而不是从零创建
记录。

### 各渠道渲染什么 [#what-each-channel-renders]

渲染按渠道进行，只有两个渠道会读取上面这些行：

| 渠道 | 基于什么渲染 |
|---|---|
| **邮件** | 匹配（主题、`email`、locale）的通知模板。没有匹配的启用行时，原样发送通知自身的标题和正文 |
| **短信** | 匹配（主题、`sms`、locale）的通知模板，回落方式相同 |
| **应用内收件箱** | **不是通知模板。** 收件箱行由通知自身的标题和正文写成 —— 生产方没有设置标题时就用主题。当通知指定的是一个邮件模板时，收件箱会渲染那个模板：通过邮件服务按（名称、locale）解析的一行 `sys_email_template`，[邮件](/docs/configure/email#templates)中有说明。如果没有能渲染它的邮件服务，这次投递会失败，而不是回落 |

> **警告：** `inbox` 是**默认**渠道 —— 没有指定渠道的通知只会投递到那里。
> 所以管理员最可能在看的那次投递，恰恰是从不读取通知模板的那一次：在这里
> 编辑模板行会改变邮件和短信发送的内容，而对应用内消息毫无影响。本页描述的
> 是现有的接线方式；它并不预告收件箱与这些行之间会有衔接。
