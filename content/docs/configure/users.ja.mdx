デプロイメントに*誰が存在するか*に関するすべて、つまり人、その人が属する組織ツリー、共同作業するチーム、そしてその人の代わりに動作するサービスアカウントは、**Setup → People & Organization**（`/apps/setup`）で管理します。

基になるアイデンティティのオブジェクト（`sys_user`、`sys_organization`、`sys_member`、`sys_business_unit`、`sys_team`、`sys_invitation`、`sys_api_key` など）はプロジェクトのデータベースにあります。それぞれが何を表すかは、[アイデンティティ層の表](/docs/configure/permissions#layer-1--identity)を参照してください。

> **日々の管理作業の 90% は、人をポジションに割り当てることです。** ポジション、その背後にある権限セット、セキュリティのベースラインは、プラットフォームとインストールしたアプリとともに提供されます。あなたの仕事は人の側（このページで扱います）と割り当て（[アクセスの管理](/docs/configure/permissions/managing-access)で扱います）です。

## 組織を作る（事業単位） [#build-the-organization-business-units]

**Setup → People & Organization → Business Units。**

事業単位のツリーは、アクセスモデルにおける*唯一の*階層です。表示範囲の深さ（`unit`、`unit_and_below`）と委任された管理の境界を決めます。導入時に作り、組織再編のときだけ見直します。

- デフォルトの **Org Chart** タブは、ツリーを字下げされた展開 / 折りたたみ可能なツリーグリッドとしてレンダリングします。
- まずルート（種類 `company`）を作成し、次に **New** で子を追加して、フォームで **Parent Business Unit** を選びます。種類の `division` / `department` / `office` / `cost_center` は表示上のヒントで、ツリーはどれでも同じように機能します。
- 再編するには、単位を **Edit** して親を変更します。ツリービューは読み取り専用の表示です。親の付け替えはドラッグ＆ドロップではなく、レコードのフォームで行います。

似た名前の 3 つのもの、3 つの異なる役割です。混同しないでください。

| オブジェクト | 役割 |
|---|---|
| **事業単位**（`sys_business_unit`） | 階層。表示範囲の深さと委任された管理の境界を決めます |
| **チーム**（`sys_team`） | フラットな共同作業のグループ。チームは共有を*受け取り*ますが、機能を持つことはありません |
| **組織**（`sys_organization`） | テナントそのもの。会社のアカウントであって、その中のノードではありません |

> ツリーは浅く、実際の構造に忠実に保ってください。組織構造によって*人がどのレコードを見られるか*に影響するべきものなら、それは事業単位です。人がレコードを共有するためのグループにすぎないなら、それはチームです。

## 人を追加する [#add-people]

**Setup → People & Organization → Users。** 入口は 3 つあり、どれも第一級の方法です。

| 経路 | 使う場面 | 起こること |
|---|---|---|
| **Invite User**（ツールバー） | 本人に届くメールアドレスがある | 招待を送ります。本人は承諾時に自分でパスワードを設定します |
| **Create User**（ツールバー） | メールのフローを使いたくない、または電話番号だけのスタッフ | すぐにサインインできるアカウント（メールアドレスと電話番号のいずれかまたは両方）を作成します。生成された一時パスワードが**一度だけ**表示され、初回ログイン時にパスワードの変更が強制されます |
| **Import**（ツールバー） | CSV/Excel からの一括の受け入れ | 列の対応付けとドライランのプレビューを備えたウィザード。1 バッチあたり最大 500 行です。サインインのポリシーを選びます。デフォルトの **auto**（16.0）は、届くすべての行を招待し、届かない行に対してだけワンタイムの一時パスワードにフォールバックします。または明示的に選びます：パスワードなし（OTP / マジックリンク / リセットリンクで初回サインイン）、招待を送る、ワンタイムの一時パスワード |

保留中の招待は **Setup → People & Organization → Invitations** に一覧されます。

セルフ登録を開かない限り、人が自分でアカウントを作成することはできません。ObjectStack 17.3 以降、サインアップの Audience のデフォルトは**招待のみ**で、人が入ってくるのはこれら 3 つの経路です。これらは Audience の設定にかかわらず機能します。人が自分でサインアップできるようにするには、[Authentication → Who may sign up](/docs/configure/authentication#who-may-sign-up-objectstack-173) を参照してください。

同じフローは、スクリプトによる受け入れのために REST でも利用できます（ObjectStack 14.3+）。

```bash
# Create a sign-in-ready account with an optional one-time password
curl -X POST https://crm.example.com/api/v1/auth/admin/create-user

# Bulk-import rows / CSV / XLSX (max 500 rows), with dry-run and upsert modes
curl -X POST https://crm.example.com/api/v1/auth/admin/import-users
```

16.0 以降、インポートのデフォルトは `passwordPolicy: 'auto'` です。配信可能なチャネル（実在のメールアドレスと接続済みのメールサービス、または SMS の招待経路を持つ電話番号）を持つ行は**招待され**、届かない行だけが一時パスワード（一度だけ返され、`must_change_password`）を受け取ります。アイデンティティだけを作る旧来の動作にするには、`passwordPolicy: 'none'` を明示的に渡します。行ごとの結果は `rows[].delivery` に現れ、`summary.delivery` に内訳があります。

ペイロード、パスワードのポリシー、電話番号だけのアカウントについては、[Authentication → Admin user management](/docs/configure/authentication#admin-user-management-objectstack-143) で扱っています。

## 組織メンバーシップの階層 [#organization-membership-tiers]

すべてのメンバーシップの行（`sys_member`）は**階層**を持ちます。ユーザーが組織の中で持つ立場です。この語彙は閉じていてプラットフォームが所有しています（ADR-0108）。次の 4 つの値だけで、アプリが何を宣言してもそれが広がることはありません。

| 階層 | 意味 |
|---|---|
| `owner` | 組織の最上位の立場。どの階層でも招待でき、ほかの owner を削除できる唯一の階層です |
| `admin` | 組織を管理します。`owner` 以外のどの階層でも招待できます |
| `delegated_admin` | 組織の管理者で**なくても**、組織への招待を発行できます。届く範囲はそれですべてです。階層そのものは何の権限にも解決されません。下記を参照してください |
| `member` | 通常の立場。管理上の到達範囲はありません。アクセスは、ほかの全員と同じく、ポジションと権限セットを通じて得られます |

> **このページでは、2 つの異なるレコードが「メンバーシップ」と呼ばれています。** `sys_member` は*どの組織に、どの階層で属しているか*に答えます。`sys_business_unit_member`（[次のセクション](#place-people-in-the-org-tree-memberships)）は*どの事業単位に属しているか*に答えます。誰かを組織ツリーに配置しても階層は変わらず、階層を変えても誰も配置されません。

階層は招待（`sys_invitation.role`）で選ばれ、メンバーシップの行（`sys_member.role`）に保存されます。どちらのフィールドも同じ 4 つの値に固定された選択リストなので、アプリケーション独自の業務上のロール（`sales_manager`）をどちらにも保存することはできず、それを指定した招待は、行が書き込まれる前に拒否されます。職務は[ポジション](/docs/configure/permissions/positions)です。

誰がどの階層を与えられるかには 2 つのルールがあります。招待は発行者自身の階層より上の階層を与えることは決してできず、`admin` より下の発行者は `member` としてしか招待できません。

**階層は何に*届く*かを決める等級であり、何を*してよいか*をまとめたものでは決してありません。** `owner` と `admin` の目に見える力は、別の仕組みから来ています。この 2 つの階層のメンバーシップには、その組織にスコープされた組織管理者の権限セットが自動的に付与されます。権限を持つのはその権限セットで、階層は誰がそれを受け取るかを決めるだけです。

### `delegated_admin` は委任された管理ではない [#delegated_admin-is-not-delegated-administration]

名前がほとんど同じ 2 つの仕組みです。間違ったほうを使ってしまうことを防ぐために、このセクションがあります。

| | `delegated_admin`（メンバーシップの階層） | [委任された管理](/docs/configure/permissions/permission-sets#delegated-administration)（権限セット） |
|---|---|---|
| 置かれる場所 | `sys_member.role` | 権限セットが持つ `adminScope` |
| 答える問い | *そもそも招待のフローに届くか？* | *実際に何を付与できるか*：どの事業単位、どの権限セットか |
| 単独での効果 | 一般のメンバーを招待できますが、誰も配置できません | 通常の割り当ての経路で管理できますが、招待は発行できません |

この 2 つは**二重にオプトインで、互いに独立しています**。スコープ付きの委任者が、新しい人を事業単位にポジション付きで配置する招待を発行できるようになるには、誰かがメンバーシップの階層を設定し、**かつ** `adminScope` を付与しなければなりません。一方を付与しても他方を付与したことにはなりません。`delegated_admin` を持っていても、[委任された管理](/docs/configure/permissions/permission-sets#delegated-administration)に挙げられている権限は何も与えられません。

## 人を組織ツリーに配置する（メンバーシップ） [#place-people-in-the-org-tree-memberships]

人を組織ツリーに配置するのは別のレコードです。**Business Unit Member** の行（`sys_business_unit_member`：ユーザー + 事業単位、1 つが*主*としてマークされます）です。深さに基づく表示範囲と `unit_and_subordinates` の共有はこのメンバーシップを通じて解決されるので、省略しないでください。メンバーシップの行を持たないユーザーは、深さに基づくルールからは見えません。

誰かが部署を移ったときは、その人の Business Unit Member の行を更新し、ポジションの割り当てを付け直します。[アクセスの管理](/docs/configure/permissions/managing-access)を参照してください。

## チーム [#teams]

**Setup → People & Organization → Teams。** チームはフラットな共同作業のグループです。共有ルールとレコードの共有はチームを対象にできますが、チームが権限セットを持つことはありません。部署をまたぐグループが、誰の職務も組織ツリーも変えずに一連のレコードを見る必要があるときに使います。

## ユーザーのライフサイクル [#user-lifecycle]

日々のライフサイクルのアクションは、各ユーザーの行のメニューとレコードのヘッダーにあります。

| アクション | 効果 |
|---|---|
| **Ban / Unban** | サインインを即座にブロック（または復元）します |
| **Unlock Account** | 総当たり攻撃によるロックアウトを早めに解除します |
| **Set Password** | パスワードを直接設定します。変更が強制されるワンタイムの一時パスワードも発行します |
| **Impersonate User** | サポートと確認のために、そのユーザーとしてセッションを開きます（セッションは記録されます） |

誰かを無効にするには、まず **Ban** します。サインインは即座にブロックされます。その後、ポジションの割り当てとメンバーシップを落ち着いて削除します。退社時の完全な手順は[アクセスの管理](/docs/configure/permissions/managing-access)にあります。

> ユーザー自身によるセルフサービスのパスワード復旧は、設定された[メール](/docs/configure/email)または SMS の配信サービスに依存します。それが接続されるまでは、管理者による **Set Password**（一時的で、変更が必須）が確実な代替手段です。

## サービスアカウントと API キー [#service-accounts--api-keys]

連携とヘッドレスのエージェントは API キー（`sys_api_key`）で認証します。**ユーザーに結び付いた**、長期間有効なプログラム用の認証情報です。キーを使ったすべての呼び出しは、そのユーザーとして、そのユーザーの権限で実行されます。

個人的なスクリプト以外では、専用のサービスユーザーを作成してください。

1. 連携のために **Create User** します（招待は不要です）。
2. 連携が扱うオブジェクトをカバーする最小の権限セットを割り当てます。管理者のセットは決して割り当てないでください。
3. **Setup → Connect an Agent** から、または REST で、そのユーザーの API キーを発行します。

```bash
curl -b cookies.txt -X POST https://crm.example.com/api/v1/keys
# → { "key": "osk_..." }  — shown once; store it in your secret manager
```

キーの使い方、ヘッダー、ローテーションについては [API アクセス](/docs/configure/api-access)で、キーによる AI エージェントの接続については [AI ツールを接続する（MCP）](/docs/configure/mcp)で扱っています。

## よくある質問 [#faq]

**新しいユーザーにほとんど何も見えません。壊れていますか？** いいえ、それはベースラインが機能しているということです。認証されたすべてのユーザーは、加算的な `member_default` のベースラインを受け取ります。本当のアクセスは、ポジションを割り当てたときに得られます。

**部署とチームの違いは？** 部署 = 事業単位（階層、表示範囲）。チーム = フラットな共有グループ。

**組み込みの権限セットを削除できますか？** いいえ。`member_default` や `organization_admin` のようなセットはプラットフォームのベースラインです。提供されたセットは上書きするか、単に割り当てずにおくことができます。
